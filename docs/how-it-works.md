# スニペット帳の守り方のしくみ（Version 2）

この文書は、`app/snippet-book.html` の中の鍵と暗号のしくみを説明します。コードでは `/*<core>` 〜 `/*</core>*/` の部分と、その下の「Passkey (WebAuthn PRF)」の部分にあたります。

## 1. 使っているもの

- すべてブラウザの WebCrypto（`crypto.subtle`）と WebAuthn（`navigator.credentials`）だけを使います。外部のライブラリは使いません。
- 暗号：AES-GCM（256bit）
- 鍵を作る：HKDF-SHA256（パスキー・復元キー）、PBKDF2-SHA256（ファイル専用パスワード・古い形のファイル）

## 2. 鍵の形

1. **データの鍵（DK）**：開くたびではなく、最初に 1 回だけ `crypto.getRandomValues` で作る 32 バイト。登録した内容はすべてこの鍵で AES-GCM 暗号化します。DK そのものは保存しません。ロックするとメモリから消します（0 で埋める）。
2. **パスキーで包む**
   - パスキーの登録で、PRF 拡張の入力（32 バイトのでたらめ）を決めます。
   - 本人確認すると、パスキーが PRF の値（32 バイト）を返します。この値は、パスキーとこのドメイン（`snippet.eiwa-up.jp`）と入力の組み合わせでしか出てきません。
   - `HKDF-SHA256(PRF の値, salt=でたらめ 16 バイト, info="snippet-book/v5/passkey")` で包む鍵を作り、DK を AES-GCM で暗号化（包む）します。
3. **復元キーで包む**
   - 復元キーは 25 文字。Crockford Base32 の 32 文字から選ぶので 5bit × 25 = 125bit です（1 バイトの下 5 ビットを使うので偏りません）。
   - 読むときは小文字・空白・`-` を許し、`O` は `0`、`I` と `L` は `1` として読みます。
   - `HKDF-SHA256(復元キー, salt=でたらめ 16 バイト, info="snippet-book/v5/recovery")` で包む鍵を作り、DK を包みます。
   - 125bit のでたらめなので、総当たりで探すことは実際にはできません。そのため PBKDF2 のような重い計算はしていません。

どちらの包みをほどいても、同じ DK が出てきます。

## 3. 保存するもの

この端末の中（localStorage）：

```
snippet-book:v5:meta = {
  version: 5,
  vaultId: でたらめ 16 バイト（base64url）,
  wraps: [
    { type: "recovery", salt, iv, ct, created },
    { type: "passkey", credId, prfSalt, label, salt, iv, ct, created },
    …
  ]
}
snippet-book:v5:data = { iv, ct }   // DK で暗号化した中身
```

バックアップファイル：

```
{ version: 5, enc: "aes-gcm", kdf: "dk-wrap", mode, role?, name, vaultId, wraps: [...], iv, ct }
```

- `wraps` には、包んだ DK だけが入ります。**PRF の値と復元キーそのものは、どこにも保存しません。**
- だから、バックアップファイルだけでは中身を読めません。パスキー（同期したものを含む）か復元キーが要ります。
- AES-GCM なので、中身を 1 ビットでも書きかえられたら開けません。

## 4. パスキーについて

- `rp.id` はページのドメイン（`snippet.eiwa-up.jp`）です。ほかのドメインからは、このパスキーの PRF の値を取り出せません。
- 登録は `residentKey: required`、`userVerification: required`、`attestation: none`。
- サーバーは使いません。チャレンジはその場で作るだけで、確かめる相手もいません。パスキーは「本人確認して PRF の値を取り出す」ためだけに使っています。
- 登録のときに PRF の値を返さない環境があるので、登録のすぐ後に 1 回だけ本人確認して値を取り出します。
- PRF に対応していない環境では、登録できたように見えても `prf.enabled` が `false` になります。そのときは包みを作らず、「対応していません」と知らせます。
- 同じ端末に二重に登録しないよう、`excludeCredentials` に登録済みのものを渡します。

## 5. 守れるもの・守れないもの

| 起きること | 結果 |
|---|---|
| バックアップファイルを盗まれ、総当たりされる | 読まれない（鍵が長いでたらめなため） |
| 開くときにのぞき見・キー入力を盗まれる | 打つものが無いので取られない（パスキーのとき） |
| ロックが外れた端末を取られる | パスキーで開けてしまう（端末のロックが大事） |
| 復元キーとバックアップを両方取られる | 読まれる（別々にしまうこと） |
| ページに悪いスクリプトを入れられる | 読まれる。CSP・別ドメイン・ハッシュ値の照らし合わせ（このリポジトリの verify）で防ぐ |

## 6. ほかのファイル

- **セット送信・ファイル専用パスワード**：人が決めるパスワード（またはアプリが作るパスフレーズ）から PBKDF2-SHA256 で鍵を作ります。新しく作るファイルは 60 万回で、回数をファイルに書きます。
- **Version 1 のファイル**：PBKDF2-SHA256 25 万回（回数の記録なし）として開きます。取り込みのときだけ使います。

## 7. 配り方

- `https://snippet.eiwa-up.jp/` から配っています。CSP は `default-src 'none'`、`connect-src 'none'`、`frame-ancestors 'none'` などです。インラインのスクリプトとスタイルを許しています（HTML 1 枚のため）。
- 配っている中身がこのリポジトリと同じかは、`.github/workflows/verify.yml` が毎日確かめます。
